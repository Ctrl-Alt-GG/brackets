# Backend security and robustness review

Reviewed scope: `backend/bracket` and the application startup/configuration code. This is a code review focused on real security and robustness risks, not a full penetration test.

## Executive summary

The backend has a generally clean structure and uses bcrypt for password hashing, but there are several important weaknesses in the default configuration, auth posture, and file-upload handling that should be addressed before production use. The most important issues are the permissive CORS defaults, hard-coded development secrets, weak brute-force protection, and unvalidated media uploads being stored under a publicly served static path.

## Findings

| Severity | Finding | Evidence | Why it matters | Suggested fix |
| --- | --- | --- | --- | --- |
| High | Over-permissive CORS with credentials enabled | [backend/bracket/app.py](backend/bracket/app.py) sets `allow_credentials=True` and `allow_origins=config.cors_origins`; [backend/bracket/config.py](backend/bracket/config.py) defaults `cors_origins` to `*` | In production, an unrestricted CORS policy with credentialed requests can expose authenticated sessions to cross-origin JavaScript on attacker-controlled sites. This is especially risky when the frontend is served from a different origin. | Require an explicit allowlist in production and disable credentialed cross-origin access unless it is absolutely needed. Avoid wildcard origins for authenticated APIs. |
| High | Development secrets are committed to source | [backend/bracket/config.py](backend/bracket/config.py) hard-codes `admin_password` and `jwt_secret` in `DevelopmentConfig` | If a developer or deployment environment accidentally runs in development mode with these defaults, an attacker can forge JWTs or log in as the admin user. This turns a configuration mistake into a full account compromise. | Store all secrets in environment variables or a secret manager, and fail startup when production-grade secrets are missing. Remove baked-in default credentials from the repository. |
| High | No brute-force protection on login or registration | [backend/bracket/routes/auth.py](backend/bracket/routes/auth.py) exposes `/token` with no rate-limiting, lockout, or exponential backoff; [backend/bracket/routes/users.py](backend/bracket/routes/users.py) exposes registration endpoints with no throttling | Attackers can automate credential stuffing or password guessing against user accounts. Because the app has a public login endpoint and user creation flow, this can become a practical account takeover vector. | Add request throttling per IP and/or per account, rate-limit login attempts, and add temporary lockouts on repeated failures. |
| High | File uploads are not content-validated or size-limited | [backend/bracket/routes/tournaments.py](backend/bracket/routes/tournaments.py) and [backend/bracket/routes/teams.py](backend/bracket/routes/teams.py) accept `UploadFile`, check only the extension, and write directly to a static directory | A malicious user can upload a file that has a valid image extension but contains script, malware, or HTML payloads. The app then serves it from a public static mount, creating a content-delivery and potentially XSS/unsafe-rendering risk. | Validate actual MIME type and content signature; enforce strict maximum file sizes; store uploads outside the public static tree or behind a controlled content-serving layer; reject executable/script content. |
| High | Public static mount can expose uploaded artifacts and application files | [backend/bracket/app.py](backend/bracket/app.py) mounts `static` at `/{api_prefix}/static` and upload handlers store binary files there | Once a file is uploaded or if a directory is misconfigured, arbitrary writable content becomes web-accessible. This broadens the attack surface and makes it easy to leak sensitive content or serve malicious assets. | Keep uploaded file storage in a non-public directory, generate random names, and serve them through a dedicated, access-controlled route rather than the generic static mount. |
| Medium | Password policy is weak and inconsistent | [backend/bracket/models/db/user.py](backend/bracket/models/db/user.py) enforces min length 8 on password updates, but registration accepts any `password: str` with no minimum quality checks; the application does not enforce complexity, length beyond 8, or common-password rejection | Weak passwords increase the likelihood of credential compromise, especially when rate limiting is absent. | Enforce a stronger password policy (e.g. minimum 12+ length, common-password blocklist, and optional uppercase/number/symbol rules) for both registration and password change. |
| Medium | JWT implementation does not enforce additional claims or explicit audience/issuer validation | [backend/bracket/routes/auth.py](backend/bracket/routes/auth.py) decodes the token and only checks the `user` claim; there are no validation rules for issuer, audience, or token type beyond the secret | This is not automatically exploitable if the signing secret is kept private, but it weakens the trust boundaries and makes future abuse or confusion attacks more likely, especially around multi-environment deployments. | Add `iss`, `aud`, `nbf`, and token-type claims, and reject JWTs that do not match expected issuance rules. |
| Medium | Session lifetime is long and not refresh-aware | [backend/bracket/routes/auth.py](backend/bracket/routes/auth.py) sets `ACCESS_TOKEN_EXPIRE_MINUTES = 7 * 24 * 60` (one week) | One-week bearer tokens are convenient, but they increase the blast radius of a stolen token. If a device is compromised or a token leaks, the attacker has a full week of access. | Use shorter-lived access tokens with refresh tokens or enforce reauthentication after shorter windows. |
| Medium | Lack of security headers and defense-in-depth protections | [backend/bracket/app.py](backend/bracket/app.py) defines the FastAPI app but does not add HSTS, CSP, X-Frame-Options, X-Content-Type-Options, or similar security headers | Modern browsers rely on these headers to reduce attack surface even when the API is otherwise functional. Without them, the backend is more susceptible to browser-driven abuse. | Add a security middleware layer that sets standard security headers and consider a strict CSP for any HTML-serving endpoints. |
| Low | User details and password-check flows are not normalized or hardened around email case | [backend/bracket/routes/auth.py](backend/bracket/routes/auth.py), [backend/bracket/sql/users.py](backend/bracket/sql/users.py), [backend/bracket/models/db/user.py](backend/bracket/models/db/user.py) treat email addresses as case-sensitive inputs in a way that can lead to duplicate or inconsistent identities | This is not a direct exploit by itself, but it can create account confusion and make multi-email normalization harder across environments. | Normalize emails to lowercase at registration and login, and enforce uniqueness on the normalized value. |

## Additional robustness concerns

- The global exception handler returns a generic `500` for all unhandled exceptions, which is good for not leaking stack traces, but it also makes debugging harder and can hide operational issues that should be logged with more detail. See [backend/bracket/app.py](backend/bracket/app.py).
- The app logs warnings about missing CORS configuration in production, but the default configuration still makes it easy to accidentally deploy with a dangerous default. See [backend/bracket/config.py](backend/bracket/config.py) and [backend/bracket/app.py](backend/bracket/app.py).
- The upload path generation is based on `uuid4()` and extension strings, which is fine from a path traversal standpoint, but the lack of content validation and static serving makes the end-to-end result fragile and risky. See [backend/bracket/routes/teams.py](backend/bracket/routes/teams.py) and [backend/bracket/routes/tournaments.py](backend/bracket/routes/tournaments.py).

## Priority order

If I had to fix only the highest-risk items first, I would do this in order:

1. Lock down CORS defaults and fail closed in production.
2. Remove hard-coded development secrets and require runtime secret injection.
3. Add login throttling / lockout.
4. Validate uploaded file content and move uploads out of the public static tree.
5. Enforce stronger password rules.

## Bottom line

This backend is not obviously exposing a critical SQL injection or command-execution bug, but it does have several important defensive weaknesses that could lead to account takeover, abuse, and asset-serving issues in production if deployed with default settings or incomplete environment configuration.
